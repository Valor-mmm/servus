## Context

The project has no code. This design covers the one-time setup of every
structural piece that future proposals build on: the TypeScript + Hono backend
running on Cloudflare Pages Functions, the Vue 3 SPA deployed to Cloudflare
Pages, the D1 database with a migration runner, and the CI pipeline.

All platform decisions are already made and documented in
`decision_reason_for_initial_project_doc.md`. This document records the
implementation-level choices within those constraints.

## Goals / Non-Goals

**Goals:**
- Establish the directory structure, build pipeline, and testing harness
- Deploy a live health endpoint to `servus.valor.codes/api/v1/health`
- Prove the full stack works: Hono → D1 → JSON response, Vue SPA served by Pages
- Get CI green on the first PR

**Non-Goals:**
- No domain features, auth, or UI beyond a placeholder app shell
- No PWA, service worker, or offline infrastructure (Proposal 2)

## Decisions

### D1: Single `wrangler.toml` at repo root

`wrangler.toml` defines the Cloudflare Pages project: build command, build
output directory, Functions directory, and service bindings (D1 database,
R2 bucket placeholder).

```toml
name = "servus"
pages_build_output_dir = "web/app/dist"

[[d1_databases]]
binding = "DB"
database_name = "servus-db"
database_id   = "<id assigned by Cloudflare at project creation>"

[[r2_buckets]]
binding = "ASSETS"
bucket_name = "servus-assets"
```

The R2 bucket is declared now so the `Env` type includes it from day one.
No code uses it until Phase 3.

### D2: Two separate `package.json` files

Root `package.json` — backend tooling and Hono dependencies. The Workers
runtime is the consumer; Wrangler bundles `functions/` at deploy time.

`web/app/package.json` — Vue SPA dependencies. Vite builds this independently
into `web/app/dist/`. Cloudflare Pages serves that output.

Keeping them separate means `npm ci` in the Pages build only installs what
Vite needs, not Wrangler and the Workers types. CI mirrors this split.

### D3: Biome at root covers both backend and frontend

A single `biome.json` at the repo root with globs covering `src/`,
`functions/`, and `web/app/src/`. One command (`biome check`) lints and
formats the entire codebase. No per-package Biome config needed.

### D4: TypeScript configs — two tsconfig.json files

- Root `tsconfig.json` — targets the Workers runtime
  (`"lib": ["ESNext"]`, `"types": ["@cloudflare/workers-types"]`). Covers
  `src/` and `functions/`.
- `web/app/tsconfig.json` — targets the browser
  (`"lib": ["ESNext", "DOM"]`, `"types": []`). Standard Vue + Vite setup via
  `@vue/tsconfig`.

Separate configs avoid type conflicts between the Workers and DOM environments.

### D5: Migration runner via Wrangler CLI

D1 migrations are numbered SQL files in `migrations/`. Wrangler tracks applied
migrations in a `d1_migrations` table it manages automatically. There is no
custom migration runner code to write or maintain.

```bash
# local
npx wrangler d1 migrations apply servus-db --local

# production (runs as part of Pages build command)
npx wrangler d1 migrations apply servus-db
```

The Pages build command runs migrations before building the Vue SPA:
```bash
npx wrangler d1 migrations apply servus-db && cd web/app && npm ci && npm run build
```

### D6: Hono app assembly pattern

`functions/api/[[route]].ts` is the only entry point. It creates the Hono
app and mounts module routers. For the walking skeleton there is only one
router (health). Future proposals add routers here.

```ts
// functions/api/[[route]].ts
import { Hono } from 'hono'
import { healthRouter } from '../../src/health/handler'

const app = new Hono<{ Bindings: Env }>()
app.route('/api/v1', healthRouter)
export const onRequest = app.fetch
```

The `Env` type is generated by Wrangler from `wrangler.toml` and lives in
`worker-configuration.d.ts` (auto-generated, gitignored).

### D7: SPA fallback via `_redirects`

Cloudflare Pages reads a `_redirects` file from the build output directory.
One rule handles all SPA navigation:

```
/api/*  /api/:splat  200
/*      /index.html  200
```

The first rule is a pass-through (Pages Functions handle `/api/` requests
before static file serving). The second rule returns `index.html` for all
other paths, letting Vue Router handle navigation client-side.

### D8: CI jobs

One GitHub Actions workflow (`ci.yml`) with parallel jobs:

| Job | Steps |
|-----|-------|
| `typecheck` | `npm run typecheck` (backend) + `cd web/app && npm run typecheck` |
| `lint` | `biome check` (root) |
| `build` | `cd web/app && npm ci && npm run build` |
| `test-backend` | `vitest run` (vitest-pool-workers) |
| `test-frontend` | `cd web/app && npm run test` |
| `e2e` | `wrangler pages dev` → Playwright smoke test (PRs to main only) |
| `secrets` | `gitleaks detect` |
| `deps` | GitHub dependency review (PRs to main only) |
| `migrations` | `wrangler d1 migrations apply servus-db --local` against fresh D1 |

All jobs are required to pass before merge.

### D9: Playwright smoke test scope for walking skeleton

The E2E suite for this proposal is minimal — just enough to prove the full
stack is wired:

1. `GET /api/v1/health` returns `200 { "status": "ok" }`
2. `GET /` returns HTML (the Vue app shell mounts, `<div id="app">` is present)
3. `GET /some/spa/route` returns `200` (SPA fallback, not 404)
4. `GET /api/v1/nonexistent` returns `404` JSON (not HTML)

## Risks / Trade-offs

**Wrangler in CI needs Cloudflare credentials** → Cloudflare API token stored
as a GitHub Actions secret (`CLOUDFLARE_API_TOKEN`). The account ID is not
secret and lives in `wrangler.toml`. Mitigation: use a scoped token (Pages
deploy + D1 write only, no zone/DNS access).

**D1 database ID in `wrangler.toml`** → The database ID is not secret (it
requires an auth token to use). Committing it is standard Cloudflare practice.
Production and local IDs differ; local uses `--local` flag which bypasses
the ID entirely.

**Pages build command runs migrations before the build** → If a migration
fails, the deploy is blocked. This is the desired behavior — a broken
migration should never result in deployed code against an unmigrated schema.
Rollback: re-deploy the previous Pages deployment via the dashboard.

**`worker-configuration.d.ts` is auto-generated** → Must be gitignored and
regenerated (`wrangler types`) after any `wrangler.toml` binding change.
CI runs `wrangler types` before `typecheck`.

## Open Questions

- **Cloudflare account ID in `wrangler.toml`**: Confirm with human whether
  this should be committed or injected via CI secret. (Standard practice is
  to commit it — it is not a secret.)
- **`servus.valor.codes` DNS record**: Human must add a CNAME from
  `servus.valor.codes` to the Pages project domain in the Cloudflare dashboard
  after the Pages project is created. This is a one-time manual step.
